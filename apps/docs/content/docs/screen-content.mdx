Anything the browser can render can live on a device screen. The screen is a
real DOM layer composited in 3D by CSS transforms, not a texture, so text stays
sharp at every angle - React components keep their state and effects,
`<video>` keeps playing, and an `<iframe>` keeps loading. By default screens
are decorative: they render live but do not take pointer input - see
[Why screens are display-only](#why-screens-are-display-only), and
[Experimental: screens that take input](#experimental-screens-that-take-input)
for the opt-in that lets them.

```tsx
// React components: state and effects keep running on the glass
<GalaxyMockup>
  <SignupForm />
</GalaxyMockup>

// A whole page via iframe
<GalaxyMockup>
  <iframe src="https://example.com" style={{ width: '100%', height: '100%', border: 0 }} />
</GalaxyMockup>

// Video, images, anything the browser can render
<GalaxyMockup>
  <video src="/demo.mp4" autoPlay muted loop style={{ width: '100%', height: '100%', objectFit: 'cover' }} />
</GalaxyMockup>
```

A picture is the shortest path to artwork: [Images as artwork](/docs/images)
covers filling a surface with an `<img>`, printing a transparent logo on the
material, and how large the file needs to be.

## The virtual display

Your content renders into a viewport that defaults to the device's logical
resolution, for example 360×780 CSS px on the Galaxy S26 and 1032×1376 on the
13" iPad Pro. Media queries, breakpoints, and `vh`/`vw` units inside the screen
match the real device's. Pass `resolution` (the CSS pixel width
of the display) to override it; height always follows the panel's aspect ratio,
so the graphic stays true to the panel.

The full table of defaults per device is in
[Devices and resolutions](/docs/devices).

## Screen props

Every device accepts the same three screen props:

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `resolution` | `number` | per device | CSS pixel width of the virtual display; height follows the panel aspect. See [The virtual display](#the-virtual-display). |
| `surfaceBackground` | `string` | `'#000000'` | CSS background painted behind your content, under whatever you render. See [Surface background](#surface-background). |
| `surfaceStyle` | `CSSProperties` | - | Extra styles merged onto the screen wrapper (for example a custom `fontFamily`). |

Each is also a per-region override on any slot, spelled exactly the same way -
one vocabulary, whichever element you hang it off. A device's screen is a slot
too, `<XMockup.Screen>`; an object with several surfaces has one slot per
surface. [Regions and slots](/docs/quick-start#regions-and-slots) covers how
slots work.

```tsx
<GalaxyMockup>
  <GalaxyMockup.Screen resolution={412} surfaceBackground="#0b0d12">
    <Dashboard />
  </GalaxyMockup.Screen>
</GalaxyMockup>

<AFrameSignMockup>
  <AFrameSignMockup.Front surfaceBackground="#20241f"><MenuBoard /></AFrameSignMockup.Front>
  <AFrameSignMockup.Back resolution={640}><HoursBoard /></AFrameSignMockup.Back>
</AFrameSignMockup>
```

## Status bar

Phones, foldables and tablets take a `statusBar` prop that draws the system
bar across the top of the screen. `true` gives you the platform's defaults;
an object sets the clock, the meters and the ink.

```tsx
<IPhoneMockup statusBar />
<GalaxyMockup statusBar={{ time: '14:05', battery: 0.42, batteryState: 'charging' }} />
<IPadMockup statusBar={{ date: 'Tue Sep 2', color: '#1c1c1e' }} />   // dark ink for a light screen
```

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `time` | `string` | `'9:41'` | Clock face. iPad gets `'9:41 AM'`, because iPadOS prints the period. |
| `date` | `string` | - | The date beside the clock, as iPadOS shows it when "Show Date in Status Bar" is on. iPad only. |
| `signal` | `number` | `4` | Cellular bars lit, 0-4. |
| `wifi` | `number` | `3` | Wi-Fi arcs lit, 0-3. |
| `wifiGeneration` | `number` | - | The small `6` or `7` One UI hangs off the Wi-Fi fan on a Wi-Fi 6 or 7 network. One UI only. |
| `battery` | `number` | `1` | Charge level, 0-1. |
| `batteryState` | `'normal' \| 'charging' \| 'low'` | `'normal'` | Colours the fill, and adds the bolt. |
| `batteryPercent` | `boolean` | iOS `false`, One UI `true` | Show the charge as a number, where each system puts it: inside the iPhone's capsule, as `100%` beside the iPad's, inside One UI's pill. One UI 8.5 always shows it, so it is on there by default; off draws the older outline capsule. |
| `carrier` | `string` | - | Carrier name. One UI only - iOS has not shown one for years. |
| `color` | `string` | `'#ffffff'` | Ink. Pass a dark value for a light screen, the way an app picks its status-bar style. |

Which bar you get is the device's to decide, not yours: iPhones and iPads draw
the iOS one, Galaxy phones, foldables and tablets the One UI one, and the two
differ in layout as well as styling - iOS centres the clock in the ear left of
the Dynamic Island and reads signal, Wi-Fi, battery on the right; One UI sets
the clock flush to the inset and reads Wi-Fi, signal, battery.

The bar is placed from the hardware rather than from a constant. Each device
already carries its front-camera geometry, so the glyph row is centred on the
Dynamic Island or the punch hole and the band is symmetrical about it, on every
variant and at whatever `resolution` you set. That includes the Z Fold's inner
display, whose hole is off-centre: the bar clears it rather than assuming a
centred camera. In landscape there is no cutout in the way, so both platforms
fall back to a plain strip along the top.

It sits *over* your content, exactly as it does on a real device. The Flip's
cover screen does not get one (One UI's cover face has its own clock and no
status bar), and neither do laptops, monitors, watches or any of the print
objects. The bar is also exported as a component, `StatusBar`, for use outside
a mockup - see [Advanced exports](/docs/api/advanced#status-bar).

### The face it is set in

The glyphs are drawn, but the clock and the battery's digits are type, and
neither San Francisco nor One UI Sans is the library's to ship. The bar asks
for the platform's own face first, so on a Mac and on a Galaxy it is set in
the real thing, then for the closest faces a machine is likely to have:
Inter, Roboto, Segoe UI, Helvetica. It never falls back to `system-ui`, which
on Linux - and so in most headless renders - is DejaVu Sans, whose wide digits
look nothing like a phone's.

If your page loads a face of its own, point the bar at it with the
`--mockup-status-bar-font` custom property, anywhere above the canvas:

```css
:root {
  --mockup-status-bar-font: -apple-system, var(--font-inter), sans-serif;
}
```

### Laying out under the status bar

A wallpaper or a lock screen is meant to run under the bar; an app's toolbar
is not. Each screen publishes the height of the strip the system draws over -
what `env(safe-area-inset-top)` reports on the real device - in its own CSS
pixels, so your content can inset itself by exactly that much. In CSS it is
the `--mockup-safe-area-top` custom property:

```tsx
<IPhoneMockup statusBar>
  <div style={{ height: '100%', boxSizing: 'border-box', paddingTop: 'var(--mockup-safe-area-top)' }}>
    <Inbox />
  </div>
</IPhoneMockup>
```

In a component it is `safeAreaTop` from [`useSurface()`](/docs/api/mockup-info#usesurface):

```tsx
import { useSurface } from 'react-3d-mockups'

function Toolbar() {
  const { safeAreaTop } = useSurface()
  return <header style={{ paddingTop: safeAreaTop + 8 }}>Inbox</header>
}
```

The camera cutout counts even with `statusBar` off: a Dynamic Island or a
punch hole is hardware, drawn either way, and it covers the same strip of the
screen either way. A screen with no cutout in the way - a tablet, a phone in
landscape - reserves only the bar itself, so there the value is `0` while
`statusBar` is off. Laptops, monitors, watches, the Flip's cover screen and
every print surface always report `0`.

## Why screens are display-only

By default, content on the glass renders live - state, effects, video,
iframes - but pointer events never reach it: clicks, scrolling and typing all
belong to the mockup's orbit controls, so a drag anywhere (body, background,
or screen) rotates the model.

That comes from where the screen's DOM sits. A screen is real DOM composited
into a WebGL scene, and by default react-3d-mockups stacks it *under* the
canvas and masks it with the depth buffer, so anything in front of the screen
covers it exactly, pixel for pixel: a laptop's keyboard hides the screen's
reflection, a phone's proud camera ring stands over a wrap, a bus's mirrors
draw over the livery. Under the canvas, though, a pointer lands on the canvas
and never on the content.

Early versions lifted the DOM above the canvas when a screen had to take
input, and hid it behind hardware by casting a few rays. Rays can only show or
hide a whole screen, so it went wrong in both directions: content showed
through hardware that should hide it (a laptop's screen through its own
keyboard), and a screen that was mostly visible could blank out entirely. That
mode was removed. The experimental one below takes input without the trade.

## Experimental: screens that take input

`experimentalScreenInput` lets pointers reach the screens. Clicks, hover,
wheel and touch scrolling, focus and typing work on the content as they do on
the page, iframes included.

```tsx
<LaptopMockup experimentalScreenInput>
  <YourApp />
</LaptopMockup>
```

Each screen's DOM moves above the canvas and is clipped every frame to the
part of it no hardware covers. The clip comes from the canvas itself: the
screen's depth mask still renders, and it leaves the canvas transparent
exactly where the screen is the nearest surface. So the clip follows the same
per-pixel test as the default, and a laptop seen from below still hides the
bottom of its display behind its base.

It is experimental: the name and the behavior may change in any release. What
it costs:

- **A readback every frame.** After each frame the canvas draws, every screen
  reads the canvas's pixels under it back from the GPU, which makes the CPU
  wait for the frame to finish.
- **About 2 KB gzip, on demand.** The clipping and dragging code loads the
  first time a screen takes input; a mockup with it off never downloads it.
- **Screens join the accessibility tree**, as `screenAccessibility="visible"`
  puts them: content that takes input has to be reachable without a pointer
  too.

### Who gets a drag

A tap or a click on a screen is always the content's. A drag is decided in
this order:

1. With `screenDrag={false}`, every drag on the screens is the content's. Set
   it on the mockup for all its screens, or on one slot
   (`<LaptopMockup.Screen screenDrag={false}>`) for one screen.
2. A drag that starts on a form control (a text field, a slider, a select,
   editable text), inside anything marked `data-mockup-no-rotate`, or one the
   content claims with `setPointerCapture` stays the content's.
3. Otherwise, once the pointer has moved 10 px, the drag turns the model, and
   the content gets no click for it.
4. On touch, a mostly vertical swipe scrolls instead, as it does on the rest
   of the mockup.

Drags on the hardware and on the background always turn the model, and with
`controls={false}` there is nothing to turn, so the content keeps every drag.

```tsx
<LaptopMockup experimentalScreenInput>
  <LaptopMockup.Screen>
    <Dashboard>
      {/* A chart you scrub by dragging: it keeps its drags, the rest turns the model. */}
      <div data-mockup-no-rotate>
        <ScrubbableChart />
      </div>
    </Dashboard>
  </LaptopMockup.Screen>
</LaptopMockup>
```

```tsx
{/* A map: drags all over it, so none of them turn the model. */}
<IPadMockup experimentalScreenInput screenDrag={false}>
  <MapApp />
</IPadMockup>
```

Drag code that only listens for `mousemove` on `document`, without capturing
the pointer, cannot be detected from outside, and loses its drag to the model
after 10 px. Mark it `data-mockup-no-rotate`, or turn `screenDrag` off for that
screen.

## React context on the screen

A screen renders into a React root of its own - its DOM has to live outside the
canvas - but context from providers above the mockup still reaches it: the
library bridges it across. A theme, an i18n provider, a router or a data client
around your page works on the glass without being repeated inside it.

```tsx
const queryClient = new QueryClient()

<QueryClientProvider client={queryClient}>
  <ThemeProvider theme="dark">
    <GalaxyMockup>
      <Dashboard /> {/* reads both providers */}
    </GalaxyMockup>
  </ThemeProvider>
</QueryClientProvider>
```

A provider inside the mockup, wrapped around the screen content, works too.
The one thing to watch is portals: a modal, tooltip or toast that portals into
`document.body` renders on the page, not on the screen. Keep anything that
should appear on the glass inside the screen's own tree.

## Screens and assistive technology

Screen content is decorative by default, the same way a product photo is: every
screen layer is marked `aria-hidden` and `inert`, so screen readers skip it and
the Tab key never lands in it. That keeps a demo's headings and buttons out of
your page's outline. The canvas itself has `role="img"` and an accessible name
(`label`) that describes the model.

When the screen carries meaningful text that appears nowhere else on the page,
expose it:

```tsx
<IPadMockup screenAccessibility="visible">
  <PricingTable />
</IPadMockup>
```

See [Accessibility](/docs/accessibility) for the rest.

## Surface background

`surfaceBackground` paints *underneath* your content - black on lit screens;
on a print object whose `color` is its stock (a card, a carton, a bag, a record
jacket, a vehicle's paint), that `color`, so your content prints onto the
material; white on the other print surfaces. It only shows where your content
does **not** paint:
a logo on a transparent PNG, a layout shorter than the surface, rounded corners
on a card, the moment before an `<iframe>` finishes loading.

Pass full-bleed opaque artwork and you will never see it. That is why nudging
it in these demos looks like it does nothing - every demo here ships art that
covers the whole surface.

Do **not** set it to `transparent` hoping the hardware shows through. A
screen's DOM sits under the canvas (see [above](#why-screens-are-display-only)),
so transparent pixels fall through to the page behind the mockup, and the screen
reads as a hole cut in the device. If you want the glass to look off, use a dark
color.

```tsx
{/* a logo centered on brand color, not stretched to the corners */}
<IPadMockup surfaceBackground="#1d4ed8">
  <YourLogo />
</IPadMockup>
```

## Touch behavior

On touch devices the mockup never traps page scrolling: vertical swipes over
the canvas or the screen scroll the page natively, and horizontal drags rotate
the device. Turning `zoom` on hands two-finger gestures on a touch screen to
the canvas instead, so page scrolling then starts outside the mockup. A
trackpad is different: its two-finger scroll passes through to the page even
with `zoom` on, and only a pinch zooms.
