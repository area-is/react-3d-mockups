Anything the browser can render can live on a device screen. The screen is a
real DOM layer composited in 3D by CSS transforms, not a texture, so text stays
vector crisp at every angle - React components keep their state and effects,
`<video>` keeps playing, and an `<iframe>` keeps loading. Screens are
decorative: they render live but do not take pointer input - see
[Why screens are display-only](#why-screens-are-display-only).

```tsx
// React components: state and effects keep running on the glass
<GalaxyMockup>
  <SignupForm />
</GalaxyMockup>

// A whole page via iframe
<GalaxyMockup>
  <iframe src="https://example.com" style={{ width: '100%', height: '100%', border: 0 }} />
</GalaxyMockup>

// Video, images, anything the browser can render
<GalaxyMockup>
  <video src="/demo.mp4" autoPlay muted loop style={{ width: '100%', height: '100%', objectFit: 'cover' }} />
</GalaxyMockup>
```

## The virtual display

Your content renders into a viewport that defaults to the device's logical
resolution, for example 360×780 CSS px on the Galaxy S26 and 1032×1376 on the
13" iPad Pro. Media queries, breakpoints, and `vh`/`vw` units inside the screen
behave exactly like on the real device. Pass `resolution` (the CSS pixel width
of the display) to override it; height always follows the panel's aspect ratio,
so the graphic stays true to the panel.

The full table of defaults per device is in
[Devices and resolutions](/docs/devices).

## Screen props

Every device accepts the same three screen props:

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `resolution` | `number` | per device | CSS pixel width of the virtual display; height follows the panel aspect. See [The virtual display](#the-virtual-display). |
| `surfaceBackground` | `string` | `'#000000'` | CSS background painted behind your content, under whatever you render. See [Surface background](#surface-background). |
| `surfaceStyle` | `CSSProperties` | - | Extra styles merged onto the screen wrapper (for example a custom `fontFamily`). |

Each is also a per-region override on any slot, spelled exactly the same way -
one vocabulary, whichever element you hang it off:

```tsx
<AFrameSignMockup>
  <AFrameSignMockup.Front surfaceBackground="#20241f"><MenuBoard /></AFrameSignMockup.Front>
  <AFrameSignMockup.Back resolution={640}><HoursBoard /></AFrameSignMockup.Back>
</AFrameSignMockup>
```

## Status bar

Phones, foldables and tablets take a `statusBar` prop that draws the system
bar across the top of the screen. `true` gives you the platform's defaults;
an object sets the clock, the meters and the ink.

```tsx
<IPhoneMockup statusBar />
<GalaxyMockup statusBar={{ time: '14:05', battery: 0.42, batteryState: 'charging' }} />
<IPadMockup statusBar={{ date: 'Tue Sep 2', color: '#1c1c1e' }} />   // dark ink for a light screen
```

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `time` | `string` | `'9:41'` | Clock face. iPad gets `'9:41 AM'`, because iPadOS prints the period. |
| `date` | `string` | - | The date beside the clock, as iPadOS shows it when "Show Date in Status Bar" is on. iPad only. |
| `signal` | `number` | `4` | Cellular bars lit, 0-4. |
| `wifi` | `number` | `3` | Wi-Fi arcs lit, 0-3. |
| `wifiGeneration` | `number` | - | The small `6` or `7` One UI hangs off the Wi-Fi fan on a Wi-Fi 6 or 7 network. One UI only. |
| `battery` | `number` | `1` | Charge level, 0-1. |
| `batteryState` | `'normal' \| 'charging' \| 'low'` | `'normal'` | Colours the fill, and adds the bolt. |
| `batteryPercent` | `boolean` | iOS `false`, One UI `true` | Show the charge as a number, where each system puts it: inside the iPhone's capsule, as `100%` beside the iPad's, inside One UI's pill. One UI 8.5 always shows it, so it is on there by default; off draws the older outline capsule. |
| `carrier` | `string` | - | Carrier name. One UI only - iOS has not shown one for years. |
| `color` | `string` | `'#ffffff'` | Ink. Pass a dark value for a light screen, the way an app picks its status-bar style. |

Which bar you get is the device's to decide, not yours: iPhones and iPads draw
the iOS one, Galaxy phones, foldables and tablets the One UI one, and the two
differ in layout as well as styling - iOS centres the clock in the ear left of
the Dynamic Island and reads signal, Wi-Fi, battery on the right; One UI sets
the clock flush to the inset and reads Wi-Fi, signal, battery.

The bar is placed from the hardware rather than from a constant. Each device
already carries its front-camera geometry, so the glyph row is centred on the
Dynamic Island or the punch hole and the band is symmetrical about it, on every
variant and at whatever `resolution` you set. That includes the Z Fold's inner
display, whose hole is off-centre: the bar clears it rather than assuming a
centred camera. In landscape there is no cutout in the way, so both platforms
fall back to a plain strip along the top.

It sits *over* your content, exactly as it does on a real device - laying out
underneath it is your business. The Flip's cover screen does not get one (One
UI's cover face has its own clock and no status bar), and neither do laptops,
monitors, watches or any of the print objects.

## Why screens are display-only

A mockup is a picture of a device, not a device. Content on the glass renders
live - state, effects, video, iframes - but pointer events never reach it:
clicks, scrolling and typing all belong to the mockup's orbit controls, so a
drag anywhere (body, background, or screen) rotates the model.

That is a deliberate architectural choice, and it is what buys the mockup its
looks. A screen is real DOM composited into a WebGL scene, and where that DOM
sits in the stacking order decides how hardware can hide it. react-3d-mockups
always stacks it *under* the canvas and masks it with the depth buffer, so
anything in front of the screen covers it exactly, pixel for pixel: a laptop's
keyboard hides the screen's reflection, a phone's proud camera ring stands over
a wrap, a bus's mirrors draw over the livery.

The alternative - lifting the DOM above the canvas so pointers can reach it -
means nothing in the scene can visually cover it any more. Hiding becomes
all-or-nothing, guessed from sample rays, and it goes wrong in both directions:
content shows through hardware that should hide it (you can see a laptop's
screen through its own keyboard), and a screen that is mostly visible can blank
out entirely. Mockups exist to look right, so that trade is not offered.

If you need a genuinely usable embedded app, render it in the page next to the
mockup rather than on it.

## Surface background

`surfaceBackground` paints *underneath* your content - black on lit screens,
white on print surfaces. It only shows where your content does **not** paint:
a logo on a transparent PNG, a layout shorter than the surface, rounded corners
on a card, the moment before an `<iframe>` finishes loading.

Pass full-bleed opaque artwork and you will never see it. That is why nudging
it in these demos looks like it does nothing - every demo here ships art that
covers the whole surface.

Do **not** set it to `transparent` hoping the hardware shows through. A
screen's DOM sits under the canvas (see [above](#why-screens-are-display-only)),
so transparent pixels fall through to the page behind the mockup, and the screen
reads as a hole cut in the device. If you want the glass to look off, use a dark
color.

```tsx
{/* a logo centered on brand color, not stretched to the corners */}
<IPadMockup surfaceBackground="#1d4ed8">
  <YourLogo />
</IPadMockup>
```

## Touch behavior

On touch devices the mockup never traps page scrolling: vertical swipes over
the canvas or the screen scroll the page natively, and horizontal drags rotate
the device. Turning `zoom` on hands two-finger gestures to the canvas instead,
so page scrolling then starts outside the mockup.
